# 银行基础资料与订单完整性

已核验并迁移本地 `vnd_bankpay`。数据库变更前，七张相关表的结构及数据已备份至 `api/runtime/bank_order_before_20261021_225145.sql`；取消权限原数据另有 runtime JSON 备份。备份包含敏感业务信息，应保留在受保护的服务器目录。

## 已实施规则

- `dt_bank_cards`、`dt_bank_user`、`dt_device_notify` 从 MyISAM 改为 InnoDB；订单、账户、流水及银行目录原本已为 InnoDB。迁移没有缩放或修改账户余额。
- 卡号按**全系统唯一**管理，不允许跨渠道或跨银行重复登记，保留原有 `UNIQUE(bank_number)`。原因是现有通知与银行卡查询接口仍通过卡号定位银行卡。卡号以字符串存储，保留前导零，写入前清除全部空白，限制6至19位数字。
- 新增/编辑银行卡在事务中校验银行存在、BIN有效、户名属于该银行卡的渠道。启用卡片还要求银行与户名已启用；停用资料可以保留关联已停用的银行或户名。
- 有订单引用的银行、户名、银行卡不物理删除，改为停用；被银行卡引用的银行与户名也保留并停用。没有引用的资料可删除。渠道只能操作自己的资料。基础资料锁与下单校验锁配合，避免边下单边删除时产生悬空引用。
- 已有引用的银行卡不能修改卡号；银行代码已有银行卡或订单引用时也不能修改。可另建新资料；名称、BIN、户名等后续修改不改变旧订单快照。
- 管理员订单不提供删除或人工取消操作，对应人工取消接口与权限均已移除。只保留原有超时退款任务，内部调用 `OrderService::expireOrder`：核对超时条件、锁定订单，通过 `BalanceService::change` 退还渠道余额、写退款流水并关闭订单，保留原订单。
- 重复超时处理核对退款流水，不能重复退款；历史已关闭但没有退款记录的订单进入人工核查。已支付或已结算订单不能执行超时退款。确认与超时处理共用订单行锁，竞争时只有一个合法资金结果。
- 金额、余额和限额均使用整数，数字部分最多13位，上限为 `9999999999999`。余额调整允许同等范围的负数，账户余额和变动后余额不得为负数或超过上限；前后端均校验。相关数据库金额字段统一具备BIGINT容量，不做单位换算，不缩放旧数据。
- 银行及订单相关10个列表页复用 `useTableList`：最新请求保护、筛选重置、分页修正、汇总数据和删除反馈；表单提交独立加载、必填校验、密码遮挡，订单操作有逐行防重复处理。

## 快照与历史回填

订单新增 `bank_card_id/bank_user_id/bank_code/bank_bin/bank_name/bank_short_name/account_name/snapshot_source`。原有 `bank_number` 作为收款卡号快照保留。新订单在基础资料锁定后保存快照并扣款，均位于同一事务。

支付页面只读订单快照，不再关联当前银行卡或当前户名生成二维码，也不读取旧版二维码缓存；缓存有效期不超过订单期限。已完成、已关闭或过期订单不可继续生成付款页。

历史快照来源：

- `created`：下单时真实保存的收款资料。
- `legacy_backfill`：迁移时按当前仍存在且渠道归属一致的关联资料回填，**不能保证等于订单创建时的原始资料**。本次初始回填3笔。
- `missing`：无法补齐。初始核验有3笔订单缺少当前银行卡关联，已保留原订单与卡号并标记缺失；支付页面提示人工核查，禁止用其他资料替代生成二维码。
